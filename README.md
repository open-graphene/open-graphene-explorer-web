# Open Graphene Explorer Web

React + TypeScript application built with Vite and TanStack Router. Styles use Vanilla Extract.

## Development

Requires Node.js 22.12+ and pnpm 10.15.0. The Node.js minimum follows the Open Graphene SDK.

This application uses local `workspace:*` packages. Install from the Mirrorboards workspace containing the Swaplock Query client and Open Graphene checkout; a standalone clone of this repository is not sufficient.

From this directory:

```sh
pnpm install
pnpm dev
```

Vite prints the local development URL. In the Mirrorboards workspace, the package is also available as `@open-graphene/explorer-web`:

```sh
pnpm --filter @open-graphene/explorer-web dev
```

## Checks and production build

```sh
pnpm typecheck
pnpm format:check
pnpm test
pnpm test:browser
pnpm test:assets:browser
pnpm test:accounts:browser
pnpm build
pnpm preview
```

The production output is in `dist/`. Configure the production web server to serve `index.html` for application routes, including `/explorer/blocks`, `/explorer/assets`, `/explorer/accounts` and `/about`, so direct navigation and refresh work.

## Routing and styles

- `src/main.tsx` creates and registers the typed router.
- `src/routes/__root.tsx` provides the shared layout and not-found page.
- `/` redirects to `/explorer/blocks`; `/about` remains available.
- `src/routes/explorer.blocks.tsx` mounts the blocks screen from `src/features/blocks/`.
- `src/routeTree.gen.ts` is generated by TanStack Router; do not edit it manually. Vite updates it during development and `pnpm typecheck` regenerates it before checking types.
- `src/styles.css.ts` and `src/features/blocks/blocks.css.ts` contain Vanilla Extract styles.

Add route files under `src/routes/`. Keep styles and other non-route modules outside that directory.

Setup follows the [TanStack Router quick start](https://tanstack.com/router/latest/docs/quick-start) and [Vite integration](https://tanstack.com/router/latest/docs/installation/with-vite).

Read-only screens are implemented at `/explorer/blocks`, `/explorer/assets`, `/explorer/accounts`, `/explorer/witnesses`, `/explorer/committee` and `/account/$accountName`. Wallet operations are not implemented.

## Explorer and wallet reference

The reference UI is https://portal.swaplock.chainpool.online/explorer/blocks.
The matching source is `mirrorboards-core/mirrorboards-swaplock/swaplock-portal`,
not `swaplock-wallet` (the latter contains CLI wallet files).

Inspected on 2026-10-03: the live blocks page, `app/components/Explorer/Explorer.jsx`,
`app/components/Explorer/Blocks.jsx`, `app/actions/BlockchainActions.js` and
`app/stores/BlockchainStore.js`. The portal uses `bitsharesjs`, `bitsharesjs-ws`
and Alt stores. These are reference implementations, not dependencies of this app.

The original explorer has blocks, assets, pools, accounts, witnesses, committee,
markets and fees tabs. Its blocks screen shows chain statistics, block-time and
transaction charts, recent activity and recent blocks. It initially requests
20 blocks, while the store retains up to 30. Block rows link to block details
and witness accounts. The displayed average confirmation time is a calculation
from recent block intervals; it should not be presented as irreversible finality.

### Selected dependencies

| Package                                  | Responsibility                                                                                                  |
| ---------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `@swaplock-query/api-ts-client`          | Generated HTTP client for indexed blocks, transactions, operations, accounts, assets and other query endpoints. |
| `@open-graphene/chain-swaplock-api`      | Typed Swaplock connection, current chain state, subscriptions and transaction lifecycle.                        |
| `@open-graphene/chain-swaplock-react`    | React provider, read/live hooks and transaction preparation hooks.                                              |
| `@open-graphene/chain-swaplock-bindings` | Protocol types, operation factories and checked codecs.                                                         |
| `@open-graphene/core`                    | Amount formatting, account validation and authority helpers.                                                    |
| `@open-graphene/fc`                      | Signing, wallet and memo primitives for later wallet stages.                                                    |
| `@tanstack/react-query`                  | Query cache and the React SDK's required peer dependency.                                                       |

`@open-graphene/primitives` supplies checked object IDs. Shared React, transport and codec packages arrive transitively. The
multi-chain `@open-graphene/graphene` facade and BitShares packages are not needed
for the initial Swaplock scope. The two compact charts use SVG; no chart library is required.

### Data mapping for the first stages

The generated HTTP methods below are exported by the `graphene_swaplock_indexer`
namespace from `@swaplock-query/api-ts-client`.

| Reference feature                                             | Available API / proposed integration                                                                                                                                                      |
| ------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Recent blocks and block lookup                                | `grapheneSwaplockIndexerBlocksGetLatestQuery`, `grapheneSwaplockIndexerBlocksGetListQuery`, `grapheneSwaplockIndexerBlocksGetByNumberQuery`, `grapheneSwaplockIndexerBlocksGetByIdQuery`. |
| Block transactions and operations                             | `grapheneSwaplockIndexerTransactionsGetByBlockQuery`, `grapheneSwaplockIndexerOperationsGetByBlockQuery`; resolve witness account names separately where necessary.                       |
| Head block, recent misses and live status                     | SDK `database.getDynamicGlobalProperties` and React `useDynamicGlobalProperties({ live: true })`.                                                                                         |
| Active witnesses, committee and chain parameters              | SDK `database.getGlobalProperties`; indexed lists for browsing.                                                                                                                           |
| Current and confidential supply                               | Read the core asset and its dynamic data through the SDK; format raw amounts using asset precision.                                                                                       |
| Block-time, transactions/second and transactions/block charts | Derive from the same recent-block window as the reference; daily indexer aggregates serve a different time scale.                                                                         |
| Recent activity                                               | Indexed operations with generated types; later implement operation-specific presentation.                                                                                                 |
| Wallet operations                                             | SDK prepare → sign → broadcast → wait for inclusion, with signer ownership and key storage designed in a separate stage.                                                                  |

Indexed data can lag behind the live head. Keep those heights distinct and show
loading, empty, unavailable and stale states explicitly. When implementing data
access, use generated SDK functions rather than handwritten endpoint calls.
The application owns and closes the chain client. `SwaplockProvider` runs inside
`QueryClientProvider`; Vite deduplicates React and TanStack Query across nested SDK workspaces.

### Local SDK build

`pnpm dev`, `pnpm typecheck` and `pnpm build` build the application's workspace
dependencies first because Open Graphene exports compiled `dist/` artifacts.
Run `pnpm build:dependencies` explicitly when needed. If generated SDK sources
are absent in a fresh Open Graphene checkout, follow that SDK's `pnpm generate`
instructions before building; generation requires its Rust toolchain/specs.

## Implemented blocks screen

Copy `.env.example` to `.env.local` to override the public read endpoints:

- `VITE_SWAPLOCK_QUERY_URL`: generated HTTP query client, default `https://query.swaplock.chainpool.online`.
- `VITE_SWAPLOCK_NODE_URL`: SDK WebSocket connection, default `wss://node01.swaplock.chainpool.online:8090`.

Only public endpoints belong in Vite environment variables; they are included in the browser bundle.

The page polls the last 30 indexed blocks and latest 16 regular operations every
three seconds while mounted and the tab is active. It displays 20 block rows.
Witness names refresh every minute. Live network head/missed-block data uses the
SDK subscription; committee/witness counts and core-asset supply refresh every
15 seconds. Navigating away releases polling observers and closes the node client.

### Comparison with the original

- Preserved: dark four-column statistics grid, two compact charts, activity/block
  panels, block/witness links, and whole-unit supply rounding. Desktop panels
  scroll independently; smaller screens stack the panels and use page scrolling.
- Metrics use the latest consecutive indexed window: transactions divided by the
  elapsed interval, transactions per block, and half the mean block interval for
  the reference's confirmation estimate. Missing/invalid intervals yield no rate.
  The original starts with 20 blocks and later retains 30; this app requests 30
  immediately, so rates can initially differ on an active chain.
- Added: explicit loading/empty/error states, retry/reconnect, retained stale data,
  indexer-vs-network height, visible latency in block counts, and a zero-clamped
  relative time when the node clock is slightly ahead of the browser.
- Activity deliberately covers only the current 30-block window and excludes
  virtual operations. The original retains up to 30 encountered transactions for
  the session, so its activity can persist longer. This first version displays
  operation names, fee payer IDs and expandable public payloads; operation-specific
  prose and account/asset resolution remain for a later stage.
- Block links open the original portal in a new tab. Witness account links open
  the local account page. Block details, remaining explorer tabs,
  login, trading and signing are not implemented. Future tabs are inactive labels.

a preview on port 5191; fixture tests cover navigation, polling cleanup, node

```

Local block and asset detail pages remain a later stage. Signing and key storage remain separate wallet work.

## Assets and accounts

`/explorer/assets` displays ID, symbol, asset type, issuer, current/max supply,
precision and last updated block. Search supports symbol or ID with contains,
prefix and exact matching. Sorting supports symbol, ID, precision and last
updated block. The initial view includes all assets.

`/explorer/accounts` displays ID, name, registrar, liquid core-asset balance,
share of current core supply and last updated block. Search supports account
name, ID, registrar name or memo key. Sorting supports name, ID, registrar name
and last updated block. A successful empty balance response means zero; a failed
balance request displays Unavailable. Percentages use integer arithmetic.

Both screens use the generated Query SDK for server-side filtering, ordering,
counts and pagination (10/25/50 rows). Filter, sort, page and size are validated
URL search parameters, preserved through reload and browser history. Changing
filters or ordering resets the page. The API's structured filters and ordering
are serialized as JSON query parameters by `src/lib/structuredQuery.ts`.

Only the visible page's details are loaded, with at most five concurrent detail
jobs. Asset reads follow the asset's dynamic-data pointer; issuer names use a
single indexed lookup. Account balances use one generated request per visible
account, plus two cached object reads for the core asset and supply. These reads
are cached for 30 seconds and can be refreshed manually. There is no list-wide
balance download or node WebSocket connection on these screens.

List failures preserve the last successful result for the same query; detail
failures leave the list visible with retry controls. Raw amounts are formatted
with the asset precision. Unsafe numeric API amounts display Unavailable rather
than silently losing precision. Indexer reads are separate requests, not an
atomic balance/supply snapshot.

The original Assets/Accounts source in `swaplock-portal` informed the tables.
Wallet contacts are outside this read-only scope. Current Query list contracts
do not expose asset issuer/type/current-supply filtering or ordering, or account
balance ordering; those controls require backend and generated-client changes.
Account and registrar/issuer links open local account details; asset detail links
explicitly open the original portal in a new tab.

The owning views live under `src/features/assets/` and `src/features/accounts/`;
shared table styles are in `src/features/explorer-list/list.css.ts` (Vanilla Extract).

## Witnesses, committee and account details

The new views prefer direct RPC through the generated Open Graphene SDK. All
currently implemented reads in these three views are available through RPC, so
they do not use Query. Existing indexed block/asset/account lists retain their
Query integration.

- `/explorer/witnesses`: the active witness set, current producer, recent-slot
  participation, per-block pay, budget and next vote tally. The table includes
  exact vote totals, missed blocks, last confirmed block, website and signing key.
  Data refreshes every 15 seconds while mounted.
- `/explorer/committee`: active members, account names, rank, exact votes and
  websites, with manual refresh. Rank follows the active-member order from the node.
- `/account/$accountName`: account identity, Activity and Balances tabs. Names and
  `1.2.x` IDs are accepted. The selected tab and history cursor are stored in the URL.

Witnesses and Committee match the reference's active-member scope, rather than
listing all standby candidates. Their search, ordering and pagination operate on
the complete active set returned by RPC, with state preserved in the URL. Websites
from chain data are linked only when they use HTTP or HTTPS.

`getGlobalProperties`, `getDynamicGlobalProperties`, `getObjects`, `getAccounts`
and asset reads supply governance data. The generated protocol union currently
returns witness/committee objects as `unknown`; narrow runtime decoders validate
the IDs, vote amounts and fields without bypassing the generated RPC transport.
Integer vote values retain full precision.

Account balances combine `getAccountBalances` and `getFullAccounts`, then resolve
asset metadata with `getAssets`. The table separates available funds, funds in
limit orders, collateral and vesting balances. Cash-back vesting is deduplicated.
All bucket totals use bigint and each asset's precision. If the node reports
truncated account collections, the view explicitly warns that locked amounts
are partial. Prices, fiat/core valuations and wallet actions are not included.

Account activity uses `history.getAccountHistory`, requests 25 operations plus
one lookahead item, and follows an inclusive RPC cursor without duplicating the
last displayed operation. Users can return to the newest activity or use browser
history to revisit pages. Operation data can be expanded; known operations have
readable names. This is the history retained by the connected node; a node may
prune older operations. There is no silent indexer fallback for an RPC error.

`src/lib/useChainConnection.ts` owns each mounted view's node connection and
closes it on navigation. Requests use the SDK timeout, and sequential reads check
cancellation before requesting dependent data. Node errors remain visible with
retry/reconnect controls. Local account links from Accounts, asset issuers,
witnesses and committee preserve browser history and list search state.

```

holdings and longer activity independent of current chain state.

## Production hosting

The deployed app is **https://explorer.mirrorboards.chat**. The Dockerfile packages
an already built `dist/` using Static Web Server; run `pnpm build` before building
the image. The runtime runs as non-root on port 3000 with SPA navigation fallback,
no-cache HTML and immutable hashed assets.

Infrastructure is managed by the platform stack at
`platforms/mirrorboards-platform/networks-platform/stacks/networks-platform-applications/applications-open-graphene-explorer/open-graphene-explorer-host-web`.
Its README documents image publication, preview/deployment, checks and rollback.
TLS and DNS use the existing Mirrorboards gateway and ExternalDNS.

Run `node tests/deployment.browser.mjs` for a read-only production smoke test of
all explorer routes, Query/RPC reads, account tabs, deep-link reload and mobile
layout. Set `EXPLORER_URL` to check another deployed environment.
